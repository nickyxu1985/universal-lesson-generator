# 教案：AI 幫我們辦園遊會 — 自動流程怎麼選（高中 × story，30 分鐘版）

> Job：w10-poc-004（v2）｜Stage 3b｜受眾：高中｜風格：story｜只讀 v2 Wiki `wiki/workflow-selection/` 00–04（Instinct 驗收 PASS）
> 概念後的 [A]–[E] 對應 Wiki 來源；標「示意」的是園遊會比喻，不是來源主張。
> v1 是 50 分鐘版（留在 git history）；v2 時間縮成 30 分鐘，但內容取自加深後的 Wiki，比 v1 多、節奏更密。

## 教學目標
學完之後，學生能夠：
1. 用「誰決定下一步」說出固定自動流、單一 Agent、Multi-Agent 的差別，並說出共同地基 augmented LLM 是什麼。
2. 認出五種固定自動流模式，各舉一個例子，並說出 orchestrator-workers 和平行化差在哪。
3. 說出 Agent 的工作迴圈、ReAct 在做什麼，以及 Agent 的代價和護欄。
4. 分辨 Multi-Agent 的兩種分工（handoffs、agents as tools），說出「什麼時候才拆」。
5. 用「由下往上問五題」替一個任務選型，並指出四個常見誤解錯在哪。

## 1. 開場故事（2 分鐘｜0–2）｜Wiki 00
- 故事（示意）：班上要辦園遊會，班長說「全部交給 AI」。可是收報名表每次做法都一樣；「讓攤位不撞名又有人潮」要邊做邊想；場地、宣傳、財務的規則又各不相同。
- 提問（30 秒）：「同樣叫 AI 幫忙，做法應該都一樣嗎？」
- 點出今天的核心問題：遇到什麼情況選哪一種，選錯了要付什麼代價。[B]
- 一句話原則先放在白板上：先找最簡單的解法，需要時才加複雜度，有時根本不需要做 agentic system。[B]

## 2. 三個名詞＋複雜度階梯（4 分鐘｜2–6）｜Wiki 00
先講情境，再講名詞；英文術語第一次出現附中文＋一句白話。

**三個名詞（1.5 分鐘）**
- **Workflow（固定自動流）**：照事先寫好的程式路線一步步做。[B][E]
- **Agent（單一 Agent）**：AI 自己決定流程和要用哪些工具。[B][E]
- **Multi-Agent（多 Agent 分工）**：不同專長的 Agent 各負責一部分；第一個要想清楚的是「每一段最後由誰回答」。[C]
- Anthropic 把這些統稱 agentic systems，但架構上把 workflow 和 agent 分開。[B]

**共同地基（1 分鐘）**
- 不管哪一種，最基本的積木都是 augmented LLM（被強化的 AI）：AI 外面加上查資料、工具、記憶，AI 會自己產生搜尋詞、挑工具、決定要記住什麼。[B][E]
- 所以「固定流程」裡的 AI 一樣可以用工具和記憶。（這點第 7 段會再考。）

**複雜度階梯（1.5 分鐘，白板畫四層）**
| 層 | 誰決定下一步 | 例子 |
|---|---|---|
| 0 單次呼叫 | 不用決定 | 問一次 AI＋查資料＋給範例，很多應用這樣就夠 [B] |
| 1 固定自動流 | 程式（事先寫好） | 五種模式（下一段）[B][E] |
| 2 單一 Agent | AI 邊做邊決定 | 在迴圈裡用工具 [B][E] |
| 3 Multi-Agent | 各分支的專家／總召 | 交棒或當工具叫 [C] |
- 往上爬，改變的只有兩件事：路徑由誰決定、最後回覆由誰負責。[B][C][E]
- 代價：越往上越有彈性，但常用延遲和成本換表現。[B]

## 3. 固定自動流：五種模式（6 分鐘｜6–12）｜Wiki 01
> 本段 6 分鐘＝故事＋核心 30 秒＋五種模式各 1 分鐘（共 5 分鐘）＋兩則提醒 30 秒。（v2 簡報第 5–6 頁照此配置）

**故事＋核心（30 秒）**
- 故事（示意）：每天把報名表整理成名單 → 檢查有沒有漏填 → 寄通知。步驟固定。
- 核心：路線事先寫好，換來可預測、做法一致，適合定義清楚的任務。[B][E]

**五種模式，每種 1 分鐘（共 5 分鐘）：做法＋來源例子＋園遊會對照**
| 模式 | 怎麼做 | 來源的例子 | 園遊會（示意） |
|---|---|---|---|
| Prompt chaining（一步接一步） | 每步處理上一步的結果，中間可加檢查點（gate）；用時間換準確 [B][E] | 先寫行銷文案再翻譯；先寫大綱、檢查後再寫全文 [B] | 整理名單 → 檢查漏填 → 寄信 |
| Routing（先分類再分流） | 先分類，再交給專門流程；分類要做得準 [B][E] | 客服把一般問題、退款、技術支援分開；簡單題給小模型、難題給大模型 [B] | 同學提問分「場地／繳費／其他」 |
| Parallelization（同時做） | Sectioning：拆成獨立小題同時做（加速）；Voting：同一題做很多次（提高信心）[B][E] | 一個模型回答、另一個同時篩不當內容；多個 prompt 一起找程式漏洞 [B] | 海報文案三個版本同時產生再挑 |
| Orchestrator-workers（指揮者派工） | 中央 AI 看輸入臨時拆工作、派給 worker、再彙整 [B][E] | 每次要改很多檔案的程式產品；從多個來源蒐集資料 [B] | 依今年攤位數臨時分配檢查工作 |
| Evaluator-optimizer（評分再改） | 一個產生、一個評分給回饋，改到可接受為止 [B][E] | 文學翻譯由評估者挑細節 [B] | 宣傳稿寫完由「評審」挑錯再改 |

**兩則提醒（共 30 秒）**
- 提醒一：orchestrator-workers 不是平行化——平行化的子任務是事先定好的，orchestrator-workers 是看輸入才決定。[B][E]
- 提醒二 ⚠️ 產品 vs 通則：n8n 的 Basic LLM Chain 不支援記憶和工具，那是 n8n 的產品定義 [A]；一般 workflow 的 AI 可以帶工具與記憶 [B][E]。

## 4. 單一 Agent：迴圈、ReAct、工具與代價（6 分鐘｜12–18）｜Wiki 02
- 故事（示意）：「想辦法讓攤位不撞名又有人潮。」AI 先查攤位名單（行動）→ 發現兩攤都叫「珍奶站」（觀察）→ 想到請一攤改名、再看人潮動線（推理）→ 查場地圖（行動）……沒人能事先寫好要幾步。

**一次任務怎麼跑（2 分鐘）**
1. 從使用者的指令或討論開始；任務清楚後自己規劃、自己做，需要時回頭問人。[B]
2. 每一步都要從環境拿「真實結果」（例如工具查到的資料、程式跑出的結果）判斷進度。[B]
3. 在檢查點或卡住時停下來問人；通常設停止條件，例如最多跑幾輪。[B]
4. 畫在圖上只有兩個點：AI →（要用工具嗎？）→ 工具 → 回到 AI；不用工具就結束。[E]

**ReAct：想一下、做一下（1.5 分鐘）**
- ReAct 讓 AI 交錯產生「推理」和「行動」：推理用來訂計畫、追進度、改計畫、處理例外；行動用來去外面查資料。[D]
- 在問答和事實查核測驗上，透過查 Wikipedia 減少瞎掰和錯誤一路傳下去，解題過程也比較看得懂。[D]
- 數字要講清楚比誰高：在 ALFWorld、WebShop 兩個測驗上，只給 1–2 個範例，成功率比模仿學習和強化學習方法分別高 34 和 10 個百分點；不代表所有 Agent 都會進步這麼多。[D]

**工具是 Agent 的介面（1 分鐘）**
- Agent 就是「在迴圈裡用工具的 AI」，所以工具說明要寫得像給新同學看的說明書：有範例、邊界情況、輸入格式，參數設計成不容易用錯（防呆）。[B]
- 真實例子：Anthropic 做程式 Agent 時，花在改工具的時間比改提示還多；Agent 離開根目錄後，AI 用相對路徑會出錯，改成工具一律要求絕對路徑後，AI 就能完美使用。[B]

**什麼時候用、代價（1.5 分鐘）**
- 用在開放式問題：很難預測要幾步、路線寫不死，而且你對 AI 的判斷有一定信任。[B][E]
- 適合的任務：要對話也要行動、有清楚的成功標準、能形成回饋迴圈、有人看著。例：客服、程式 Agent（能用自動測試檢查，但人工審查仍然重要）。[B]
- 代價：比較貴、錯誤可能一路累積；要先在安全環境多測、加護欄。[B]

## 5. Multi-Agent：兩種分工、什麼時候才拆（5 分鐘｜18–23）｜Wiki 03
- 故事（示意）：總召 Agent 派工給場地組、宣傳組、財務組——三組的指令、工具、規則都不同，拆開才有道理。

**兩種分工（2 分鐘）**
| 方式 | 什麼時候用 | 發生什麼事 | 園遊會（示意） |
|---|---|---|---|
| Handoffs（交棒） | 專家應該接手下一個回覆 | 控制權交給專家 [C] | 同學問「攤位在哪？」→ 交給場地組直接回答 |
| Agents as tools（當工具叫） | 總召要自己整合最後答案，專家只做摘要、分類這類小事 | 總召保有回覆 [C] | 總召寫導師報告，只請財務組算數字 |
- 來源例子：分流 Agent 把對話交給帳務或退款專家（交棒）；研究助理呼叫摘要 Agent（當工具）。[C]
- 交棒要清楚：每個專家只做一件窄的事，交棒說明短而具體。[C]

**什麼時候才拆（2 分鐘）**
- 能用一個 Agent 就先用一個。[C]
- 拆開要能明顯改善至少一項：能力隔離、規則（政策）隔離、提示更清楚、紀錄更好追。[C]
- 只有下一段真的需要不同的指令、工具或規則才拆；太早拆會多出提示、紀錄和要核准的關卡。[C]
- 分工的想法 workflow 裡早就有：routing 分流、平行化時一個回答一個把關；每個考量各用一次 AI 專心處理，通常表現更好。[B]

**和 workflow 的關係（1 分鐘）**
- Orchestrator-workers 是 workflow 裡最接近分工的模式：中央 AI 看輸入拆工作、派給 worker、各自寫進共用的地方，再合成結果。[B][E]
- 例：規劃器先列出報告章節，每個 worker 寫一節，最後合成完整報告。[E]

## 6. 選型決策：往上問五題＋選錯的症狀（4 分鐘｜23–27）｜Wiki 04
**由下往上問，答「夠了」就停（2 分鐘，白板逐題往上畫）**
1. 問一次 AI＋查資料＋範例夠不夠？夠 → 停。[B]
2. 能不能事先拆成固定步驟？能 → 選對應的固定模式（chaining／routing／平行化／評分再改）。[B][E]
3. 子任務要看輸入才知道？→ Orchestrator-workers。[B][E]
4. 連要幾步都無法預測？→ 單一 Agent，配停止條件和護欄。[B][D][E]
5. 一個 Agent 不夠清楚、各部分規則不同？→ Multi-Agent，再決定交棒或當工具。[C]
- 每往上一步都要問：多出來的時間、成本、提示和關卡值不值得？[B][C]
- 模式可以組合，例如主流程用分流，其中一個分支交給 Agent。[B]

**選錯了會怎樣（1.5 分鐘）**
| 選得太簡單 | 選得太複雜 |
|---|---|
| 不同類輸入擠一起，顧到一類就傷到另一類 [B] | 寫得死的任務用 Agent：更貴、錯誤會累積 [B] |
| 同一次呼叫又要回答又要把關，效果較差 [B] | 太早拆：提示、紀錄、關卡變多 [C] |
| 多個考量擠在一次呼叫，不如分開專心做 [B] | 為了套框架加抽象層，底層看不到、難除錯 [B] |

**出手前的檢查清單（30 秒）**
- 我說得出每一步要做什麼嗎？[B][E] 我能驗證每一步的結果嗎？[B] 我設了停止條件和人工檢查點嗎？[B] 要拆的話，各專家的指令、工具或規則哪裡不同？[C]

## 7. 常見誤解快問快答＋小測驗＋收尾（3 分鐘｜27–30）｜Wiki 00–04
**快問快答：對還是錯？（1 分鐘，學生舉手）**
- 「固定流程不能用工具或記憶」→ 錯，那是 n8n chain 節點的產品限制。[A][B][E]
- 「Agent 越多越強」→ 錯，太早拆反而增加提示、紀錄和關卡。[C]
- 「Agent 比較先進，所以一律用 Agent」→ 錯，很多應用連 agentic system 都不需要。[B]
- 「ReAct 讓所有 Agent 成功率多 34％」→ 錯，那是兩個特定測驗、對特定方法的結果。[D]

**小測驗（1.5 分鐘，3 題）**
1. 園遊會結束後，要照名單寄感謝信給每個攤位，步驟每次都一樣。選哪一種？
   - 答：固定自動流（prompt chaining）；步驟固定、可事先拆好。[B][E]
2. 要 AI 找出「為什麼今年人潮變少」，不知道要查幾次資料。選哪一種？要加什麼保護？
   - 答：單一 Agent；要設停止條件（例如最多查幾輪），並在檢查點讓人看。[B]
3. 總召要寫一份給導師的總報告，只想請財務組算好數字、自己整合。用交棒還是當工具？
   - 答：Agents as tools；總召保有最後回覆，專家只做有範圍的工作。[C]

**收尾（30 秒）**
- 一句話帶走：先用最簡單的，能證明變好才加複雜度。[B]
