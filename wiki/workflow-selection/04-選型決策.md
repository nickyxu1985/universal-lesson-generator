# 04 選型決策：遇到什麼問題，怎麼選

> Job：w10-poc-004（v2，Wiki 增量）｜主張後的 [A]–[E] 對應頁尾來源；標「示意」的是本 Wiki 的教學情境，標「本 Wiki 推論」的是由來源推出、非原文的句子。

## 一、定義

- **「選型」在這份 Wiki 的意思**：面對一個要交給 AI 自動化的任務，決定它該停在複雜度階梯的哪一層：單次 LLM 呼叫、固定自動流、單一 Agent，還是 Multi-Agent（階梯見 00 總覽）。
- **選型的核心判斷有三個**：
  1. **路徑寫不寫得死**：workflow 的路徑是預先寫好的程式；agent 由 LLM 動態決定流程與工具。[B][E]
  2. **值不值得多花成本**：agentic system 常以延遲與成本換取更好的任務表現，要考慮這筆交換何時合理。[B]
  3. **契約有沒有改變**：只有下一個分支真的需要不同的指令、工具或政策時才拆成多個 Agent。[C]
- **選型的總原則**：先找最簡單的解法，只在需要時增加複雜度，甚至可能不需要建 agentic system。[B] 要增加複雜度，必須是能證明結果變好的時候。[B]

- **選型不是一次定案**：這些模式不是規定，而是可以依用途組合與調整的常見模式；同一個系統裡可以同時出現好幾種，成功的關鍵是衡量表現、反覆改進。[B] 所以選型的答案可以是「主流程用 routing，其中一個分支再交給 agent」這類組合（組合方式為本 Wiki 舉例）。

## 二、運作方式：一步一步往上問

把選型想成一串由下往上的問題，前一題答「夠了」就停，不用往上爬：

1. **單次呼叫夠不夠？** 很多應用把單次 LLM 呼叫配上檢索與情境內範例優化好，通常就夠了。[B] → 夠了就停在這層。
2. **能不能事先拆成固定步驟？** 任務能乾淨拆成固定子任務時用 prompt chaining [B]；有明確類別、分類能做準時用 routing [B]；子任務可同時跑或需要多次嘗試時用 parallelization [B][E]；有清楚評估標準、反覆修改有可衡量價值時用 evaluator-optimizer [B]。→ 能拆就停在固定自動流。
3. **子任務要看輸入才知道？** 無法預測需要哪些子任務時，用 orchestrator-workers：由中央 LLM 依輸入動態拆解與派工。[B][E]
4. **連步驟數都無法預測？** 開放式問題、難以或無法預測需要幾步、也無法寫死路徑時，才用 agent；而且要對它的決策有一定信任。[B] → 用單一 Agent（工具迴圈），配停止條件與護欄。[B]
5. **一個 Agent 是否已經不夠清楚？** 只有拆開能明顯改善能力隔離、政策隔離、提示清晰度或追蹤可讀性時，才加專家 Agent。[C] → 再決定由專家接手（handoffs）還是管理者保有回覆（agents as tools）。[C]

每往上一步，都要回頭確認：這一步帶來的好處，是否值得多出的延遲、成本，以及更多的 prompt、trace 與核准點。[B][C]

## 三、決策表

| 遇到的情況 | 建議 | 依據 |
|---|---|---|
| 單次 LLM 呼叫＋檢索＋範例就夠 | 先不做 agentic system | [B] |
| 步驟固定、可事先拆好、要可預測 | 固定自動流（prompt chaining） | [B][E] |
| 輸入有明確類別，分開處理比較好，分類又做得準 | Routing | [B][E] |
| 子任務彼此獨立可同時跑，或要多種觀點提高信心 | Parallelization（sectioning／voting） | [B][E] |
| 有清楚評估標準，反覆修改有可衡量的價值 | Evaluator-optimizer | [B][E] |
| 子任務數量與內容要看輸入才知道 | Orchestrator-workers | [B][E] |
| 步驟數無法預測、路徑寫不死、需要模型自己判斷 | 單一 Agent（工具迴圈，ReAct 式） | [B][D][E] |
| 不同部分需要不同指令、工具或政策，且拆開能改善隔離或可讀性 | Multi-Agent | [C] |
| 專家應該負責下一個回覆 | Handoffs | [C] |
| 管理者要整合最終答案，專家只做摘要、分類等有範圍的工作 | Agents as tools | [C] |

## 四、例子

### 來源裡的例子，放回決策表
- **行銷文案→翻譯**：步驟固定，屬於 prompt chaining。[B]
- **客服問題分成一般問題、退款、技術支援**：類別明確，屬於 routing。[B] 若要讓專家 Agent 直接接手對話，則是 Triage agent 交棒給 Billing、Refund 專家的 handoffs。[C]
- **多個 prompt 一起檢查程式碼漏洞**：同一任務多次嘗試，屬於 parallelization 的 voting。[B]
- **文學翻譯反覆修稿**：有評估者給批評、迴圈改進，屬於 evaluator-optimizer。[B]
- **每次要改很多檔案的程式產品**：子任務看輸入才知道，屬於 orchestrator-workers。[B]
- **解 SWE-bench 任務、操作電腦完成任務**：步驟數無法預測，屬於 agent。[B]
- **ReAct 在 HotpotQA、Fever 透過 Wikipedia API 查證**：推理與行動交錯的 agent 迴圈，減少幻覺與錯誤傳遞。[D]

### 示意：同一個園遊會，四種選擇
| 園遊會的需求 | 選型 | 理由對應 |
|---|---|---|
| 每天整理報名名單、寄通知 | 固定自動流 | 步驟固定可拆 [B] |
| 把同學提問分成場地、繳費、其他 | Routing | 類別明確 [B] |
| 想辦法讓攤位不撞名又有人潮 | 單一 Agent | 步驟數無法預測 [B] |
| 場地、宣傳、財務規則與工具各不同 | Multi-Agent | 契約不同才拆 [C] |

## 五、適用情境與取捨

### 選型三原則
1. **由簡入繁**：只在能證明結果變好時加複雜度；這些模式可以組合與調整，關鍵是衡量表現並反覆改進。[B]
2. **Agent 是有代價的**：較高成本、錯誤可能累積，需要沙盒測試、護欄與停止條件。[B]
3. **拆 Agent 要有理由**：契約（指令、工具、政策）改變了才拆，否則多出的是 prompt、trace 與核准點。[C]

### 兩組取捨
- **可預測 vs 彈性**：任務定義清楚時，workflow 提供可預測性與一致性；需要大規模的彈性與模型自主決策時，agent 是比較好的選擇。[B]
- **框架 vs 直接寫**：框架讓入門變快，但抽象層可能遮住底層 prompt 與回應、讓除錯變難，也容易誘人加上不必要的複雜度；建議先直接用 LLM API，邁向正式上線時不要猶豫減少抽象層。[B]

### 選錯了會怎樣
**選得太簡單**（該拆沒拆）：
- 不同類型的輸入混在同一個流程裡，為某一類輸入最佳化，可能傷害其他類輸入的表現。[B]
- 讓同一次 LLM 呼叫同時處理護欄與主要回覆，效果通常不如分給兩個模型實例各做一件事。[B]
- 有多個考量的複雜任務擠在一次呼叫裡，不如每個考量各用一次獨立呼叫、專注一個面向。[B]

**選得太複雜**（不該拆卻拆）：
- 用 agent 處理其實寫得死的任務，要付出較高成本，並承擔錯誤累積的風險。[B]
- 太早拆成多個 Agent，多出 prompt、trace 與核准點，不一定更好。[C]
- 為了套框架而加上的抽象層，會遮住底層的 prompt 與回應，讓除錯更難。[B]

**本 Wiki 的整理**（推論）：太簡單的症狀通常是「某類輸入的品質一直上不去」；太複雜的症狀通常是「成本變高、錯誤難追、要核准的地方變多」。看到哪一種症狀，就往階梯的哪個方向調整一層，再用評估確認有沒有變好（「衡量表現、反覆改進」見 [B]）。

### 用一張檢查清單收尾
選定之前，至少問自己這幾題（每題對應一句來源）：
- 我能說出這個任務每一步要做什麼嗎？能 → 偏向 workflow。[B][E]
- 我有沒有辦法驗證每一步的結果？agent 需要每一步從環境取得 ground truth，程式碼 agent 有效的原因之一就是能用自動化測試驗證。[B]
- 我有沒有設停止條件與人工檢查點？[B]
- 如果要拆，我能說出每個專家的指令、工具或政策哪裡不同嗎？[C]

## 六、常見錯誤（驗收提醒）

1. **「固定流程不能用工具或記憶」** → 錯。這只是 n8n Basic LLM Chain 節點的產品限制 [A]；一般 workflow 的 LLM 可帶工具與記憶 [B][E]。
2. **「Agent 越多越強」** → 不一定，太早拆反而增加 prompt、trace 與核准點。[C]
3. **「Agent 比 workflow 先進，所以一律用 Agent」** → 錯。很多應用連 agentic system 都不需要；agent 適合的是步驟數無法預測的開放式問題。[B]
4. **「orchestrator-workers 就是平行化」** → 不是。平行化的子任務是事先定義的，orchestrator-workers 的子任務依輸入動態決定。[B][E]
5. **「ReAct 讓 Agent 成功率提高 34％」** → 不能這樣說。34 與 10 個百分點只是在 ALFWorld 與 WebShop、對上模仿學習與強化學習方法的結果。[D]
6. **「用了框架就不用懂底層」** → 錯。對框架底層的錯誤假設是常見的錯誤來源。[B]
