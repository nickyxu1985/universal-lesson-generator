# 00 總覽：自動流程選型（固定自動流 → 單一 Agent → Multi-Agent）

## 一、定義

### 1. 這份 Wiki 要回答的問題
同一件事，可以寫成一條固定的流程讓 AI 照著跑，也可以交給一個 Agent 讓它自己決定怎麼做，甚至拆給好幾個 Agent 分工。這份 Wiki 回答一個很實際的問題：遇到什麼樣的任務，該選哪一種做法，選錯了會付出什麼代價。

### 2. 總稱：agentic systems
Anthropic 觀察到「Agent」這個字有好幾種用法：有人指的是能長時間獨立運作、使用各種工具完成複雜任務的全自主系統，也有人指的是照預先定義的流程執行、規範性比較強的實作。Anthropic 把這些變體統稱為 agentic systems，但在架構上明確區分兩類：workflow 與 agent。[B]

### 3. 三個核心名詞
- **Workflow（固定自動流）**：LLM 與工具透過「預先寫好的程式路徑」被編排起來執行。[B] LangGraph 的說法是：workflow 有預定的程式路徑，設計成照一定順序運作。[E]
- **Agent（單一 Agent）**：由 LLM 動態主導自己的流程與工具使用，自己掌握完成任務的方式。[B] LangGraph 的說法是：agent 是動態的，會自己定義流程與工具使用。[E]
- **Multi-Agent（多 Agent 分工）**：讓不同的專責 Agent 各自負責工作的不同部分；第一個設計決定是「在流程的每個分支，由誰負責給使用者的最終回覆」。[C]

### 4. 共同的地基：augmented LLM
不論是 workflow 還是 agent，最基本的積木都是「被強化過的 LLM」（augmented LLM）：在 LLM 外面加上檢索、工具與記憶等能力，模型可以自己產生搜尋查詢、挑選工具、決定要保留哪些資訊。[B] LangGraph 也把 workflow 與 agentic system 的基礎描述為「LLM 加上各種強化」，例如工具呼叫、結構化輸出、短期記憶。[E]

### 5. 產品名詞不等於通用名詞
n8n 文件裡的 chain 與 agent 是 n8n 自家節點的定義：n8n 的 AI Agent 會決定要呼叫哪些工具、可以使用記憶；chain 則是一串 LLM 呼叫，不帶工具也不帶記憶。[A] 這是產品層的定義，不能直接套成「所有固定自動流都不能用工具或記憶」，因為 [B][E] 的 workflow 本身就建立在可以用工具與記憶的 augmented LLM 上。

## 二、運作方式：一條由簡入繁的複雜度階梯

把三種做法排成一條階梯，越往上，系統越有彈性，但也越貴、越難預測：

| 階梯 | 誰決定下一步 | 典型做法 | 依據 |
|---|---|---|---|
| 0. 單次 LLM 呼叫 | 不需要決定 | 把單次呼叫配上檢索與範例優化好，很多應用這樣就夠 | [B] |
| 1. 固定自動流 | 程式（事先寫好） | prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer | [B][E] |
| 2. 單一 Agent | LLM（邊做邊決定） | LLM 根據環境回饋，在迴圈裡使用工具 | [B][E] |
| 3. Multi-Agent | 多個 Agent，依分支決定誰負責回覆 | handoffs，或把專家 Agent 當工具呼叫 | [C] |

往上爬時真正改變的只有兩件事：
1. **路徑由誰決定**：階梯 1 由程式決定，階梯 2 起由模型決定。[B][E]
2. **最終回覆由誰負責**：階梯 3 要先想清楚每個分支是專家接手對話，還是管理者保有最後回覆。[C]

Anthropic 的建議是由最簡單的解法開始，只有需要時才增加複雜度，甚至可能根本不必建 agentic system。[B] 它也提醒：這些模式不是規定，而是可以依用途組合、調整的常見模式；成功的關鍵是衡量表現、反覆改進，並且只在能證明結果變好時才增加複雜度。[B]

## 三、例子

### 來源裡的例子
- **n8n 的對照範例**：一個 Chat Trigger 接收聊天訊息，Switch 節點看訊息裡寫的是「agent」還是「chain」，把問題導到 AI Agent 或 Basic LLM Chain。AI Agent 接了 Wikipedia 工具與 Simple Memory，所以能查 Wikipedia 文章，也能回答「我上一個問題是什麼？」；Basic LLM Chain 不支援記憶與工具。範例建議分別對 agent 與 chain 問同樣的問題來比較。[A]
- **Anthropic 觀察到的兩個實務領域**：客服（對話流程中需要查顧客資料、訂單紀錄、知識庫，還要執行退款、更新工單）與程式碼 Agent（解法可用自動化測試驗證、能用測試結果回饋迭代）。[B]
- **OpenAI 的分流例子**：一個 Triage agent 可以把對話交給 Billing agent 或 Refund agent 接手。[C]

### 示意：班上要辦園遊會
- 收報名表 → 整理名單 → 寄通知，每次步驟都一樣：適合固定自動流。
- 「想辦法讓攤位不撞名又有人潮」，步驟要邊做邊想：才考慮單一 Agent。
- 場地、宣傳、財務各有不同規則與工具：分工真的帶來好處時，才考慮 Multi-Agent。

（以上三點是教學比喻，判斷依據分別見 01、02、03 頁的來源主張。）

### 同一件事在三層的樣子（對照來源）
- 客服可以是 routing：先把一般問題、退款、技術支援分類，再導到不同的流程、prompt 與工具。[B]
- 客服也可以是 agent：在對話中自己查顧客資料與訂單，並執行退款或更新工單。[B]
- 客服還可以是 multi-agent：由分流 Agent 把對話交給帳務或退款專家接手。[C]
同一個領域可以落在不同層，決定落點的是任務本身能不能事先寫死，而不是領域名稱。（最後一句為本 Wiki 歸納。）

## 四、適用情境與取捨

- **用延遲與成本換表現**：agentic system 常用較高的延遲與成本，換取更好的任務表現，要先想清楚這筆交換值不值得。[B]
- **可預測 vs 彈性**：任務定義清楚時，workflow 提供可預測性與一致性；需要大規模的彈性與模型自主決策時，agent 比較合適。[B]
- **最簡單的常常就夠**：很多應用把單次 LLM 呼叫配上檢索與情境內範例優化好，通常就夠了。[B]
- **框架的取捨**：框架能簡化呼叫 LLM、定義與解析工具、串接呼叫等低階工作，但常多出抽象層，讓底層的 prompt 與回應被遮住、難以除錯，也讓人忍不住加上不必要的複雜度；建議先直接用 LLM API，用框架就要理解底層程式碼。[B]
- **Multi-Agent 的取捨**：能用一個 Agent 就先用一個；只有在能明顯改善能力隔離、政策隔離、提示清晰度或追蹤可讀性時才加專家，太早拆會多出更多 prompt、trace 與核准點。[C]
- **可解釋性**：ReAct 讓模型交錯產生推理軌跡與行動，論文指出這樣產生的解題軌跡比沒有推理軌跡的基準更容易解讀。[D]

### 貫穿全書的三條實作原則
Anthropic 在總結時提到，實作 Agent 時盡量遵守三個核心原則：[B]
1. **簡單**：讓 Agent 的設計保持簡單。
2. **透明**：明確顯示 Agent 的規劃步驟。
3. **用心設計 Agent 與電腦之間的介面（ACI）**：工具要有完整的文件，並且經過充分測試。

它也提醒：在 LLM 領域，成功不在於做出最精密的系統，而在於做出「符合需求的對的系統」；先從簡單的 prompt 開始，用完整的評估去優化，簡單方案不夠時才加入多步驟的 agentic system。[B] 這三條原則與「由簡入繁」的方向，是後面四頁共同的判斷基準。

## 五、常見錯誤

1. **一開始就做最複雜的版本**：跳過單次呼叫與固定流程，直接做 Agent 或多 Agent。來源的原則正好相反：先找最簡單的解法，只有簡單方案不夠時才加多步驟的 agentic system。[B]
2. **把 n8n 的節點限制當成通用規則**：「chain 不帶工具與記憶」是 n8n Basic LLM Chain 的產品定義 [A]，一般 workflow 的 LLM 可以帶工具與記憶 [B][E]。
3. **以為 Agent 越多越強**：太早拆 Agent，會多出更多 prompt、trace 與核准點，不一定讓流程變好。[C]
4. **只用框架、不懂底層**：對框架底層的錯誤假設，是客戶常見的錯誤來源。[B]
5. **把論文數字講成通則**：ReAct 的 34 與 10 個百分點，是在 ALFWorld 與 WebShop 兩個 benchmark、對上模仿學習與強化學習方法的結果，不是「所有 Agent 都會進步這麼多」。[D]
6. **忽略來源的時效**：Anthropic 在文章開頭註明，文中描述的工具生態自 2024 年 12 月以來已有很多改變。[B] 引用框架與工具名稱時要注意時間點，模式與原則才是本 Wiki 主要採用的部分。

## 六、本 Wiki 怎麼讀
- 01 固定自動流：五種 workflow 模式，各自怎麼運作、什麼時候用。
- 02 單一 Agent：工具迴圈、ReAct、停止條件與護欄。
- 03 Multi-Agent：handoffs 與 agents as tools，什麼時候才拆。
- 04 選型決策：把前三頁整理成一張「遇到什麼情況選哪個」的決策表與檢查清單。
