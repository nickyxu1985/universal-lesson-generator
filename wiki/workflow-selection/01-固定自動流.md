# 01 固定自動流（Workflow）

> Job：w10-poc-004（v2，Wiki 增量）｜主張後的 [A]–[E] 對應頁尾來源；標「示意」的是本 Wiki 的教學情境，不是來源主張。

## 一、定義

- **Workflow 是預先寫好路徑的系統**：LLM 與工具透過預先定義的程式路徑被編排執行。[B] LangGraph 的說法是：workflow 有預定的程式路徑，設計成照一定順序運作。[E]
- **它的強項是可預測**：對定義清楚的任務，workflow 提供可預測性與一致性。[B]
- **它不是「不能用工具的流程」**：workflow 的每一次 LLM 呼叫，都可以是帶著檢索、工具與記憶的 augmented LLM；Anthropic 在介紹各種 workflow 前就說明，之後都假設每次 LLM 呼叫都能使用這些強化能力。[B] LangGraph 也把工具呼叫、結構化輸出與短期記憶列為 workflow 與 agentic system 共同的強化選項。[E]
- **它和 Agent 的差別在「誰決定路徑」**：workflow 的路徑由程式事先決定；agent 則由 LLM 動態主導自己的流程與工具使用。[B][E]

## 二、運作方式：五種常見模式

[B] 與 [E] 列出的是同一組五種模式。下面逐一說明它怎麼跑、檢查點放在哪裡。

### 1. Prompt chaining（提示串接）
- **怎麼跑**：把任務拆成一連串步驟，每一次 LLM 呼叫處理上一步的輸出。[B][E]
- **檢查點**：可以在任何中間步驟加上程式化檢查（Anthropic 圖中稱為 gate），確保流程還在正軌上。[B] LangGraph 的範例就是這樣做：先產生一個笑話，再用一個檢查函式判斷 Pass 或 Fail；Fail 才進入「改進」與「潤飾」兩步，Pass 就直接結束。[E]
- **核心交換**：用延遲換準確度，讓每一次 LLM 呼叫都只做比較簡單的事。[B]

### 2. Routing（分流）
- **怎麼跑**：先把輸入分類，再導到專門的後續任務。[B][E]
- **好處**：讓關注點分離，可以寫更專門的 prompt；沒有分流時，為某一類輸入最佳化，可能會傷害其他類輸入的表現。[B]
- **分類器不一定是 LLM**：分類可以由 LLM 做，也可以用比較傳統的分類模型或演算法，前提是分類夠準。[B] LangGraph 的範例則是讓 LLM 以結構化輸出決定路由，再用條件邊導向對應節點。[E]

### 3. Parallelization（平行化）
- **怎麼跑**：讓多個 LLM 同時處理任務，再用程式彙整輸出。[B] 有兩種變形：[B][E]
  - **Sectioning（分段）**：把任務拆成彼此獨立的子任務同時跑，目的是加速。
  - **Voting（投票）**：同一個任務跑很多次，取得多樣的輸出，目的是提高信心。
- **為什麼有效**：面對有多個考量的複雜任務，讓每個考量各由一次獨立的 LLM 呼叫處理、專心看一個面向，LLM 通常表現更好。[B]

### 4. Orchestrator-workers（指揮者－工作者）
- **怎麼跑**：由一個中央 LLM 動態拆解任務、派給 worker LLM，再彙整結果。[B] LangGraph 描述為：拆任務、派子任務、把 worker 的輸出合成最終結果。[E]
- **和平行化的差別**：外形相似，但子任務不是事先定義好的，而是由 orchestrator 依照具體輸入決定。[B] LangGraph 用 `Send` API 動態建立 worker 節點並送出各自的輸入；每個 worker 有自己的狀態，所有輸出寫進一個共用的狀態鍵，讓 orchestrator 讀取並合成。[E]

### 5. Evaluator-optimizer（評估－優化迴圈）
- **怎麼跑**：一次 LLM 呼叫產生回應，另一次負責評估並給回饋，在迴圈中反覆進行。[B] 若評估者或人工審核（human-in-the-loop）判斷還需要修改，就提供回饋並重新產生，直到得到可接受的回應為止。[E]
- **類比**：就像作者寫出一份完善文件之前反覆修稿的過程。[B]

## 三、例子

### 來源裡的例子
| 模式 | 來源舉的例子 |
|---|---|
| Prompt chaining | 先寫行銷文案再翻譯成另一種語言；先寫大綱、檢查大綱是否符合標準，再依大綱寫全文。[B] 翻譯文件、檢查生成內容的一致性。[E] |
| Routing | 把一般問題、退款申請、技術支援分到不同的下游流程、prompt 與工具。[B] 把簡單常見的問題交給較小、較省成本的模型（如 Claude Haiku 4.5），困難少見的交給能力較強的模型（如 Claude Sonnet 4.5）。[B] 產品問答先判斷問題類型，再導到價格、退款、退貨等流程。[E] |
| Parallelization | Sectioning：一個模型處理使用者問題，另一個同時篩查不當內容，通常比同一次呼叫兼顧兩件事效果好；自動化評估時每次呼叫評一個面向。Voting：多個不同 prompt 一起檢查程式碼漏洞；用多個 prompt 與不同投票門檻判斷內容是否不當，平衡誤報與漏報。[B] 一個子任務抽關鍵字、另一個查格式錯誤；依引用數、來源數、來源品質等不同標準多次評分。[E] |
| Orchestrator-workers | 每次都要改很多檔案的程式產品；要從多個來源蒐集並分析資訊的搜尋任務。[B] 要在數量未知的文件裡更新多個 Python 套件的安裝說明。[E] |
| Evaluator-optimizer | 文學翻譯：譯者 LLM 一開始抓不到的細微差異，由評估者 LLM 提出批評。[B] 需要多輪搜尋與分析的複雜搜尋任務，由評估者決定要不要再搜。[B] 兩種語言之間翻譯不一定有完美對應，可能要幾輪才能譯出同樣意思。[E] |

### n8n 的 chain（產品例子）
- n8n 的 Basic LLM Chain 節點可以和接上的 LLM 對話，但不支援記憶與工具；n8n 的 chain 不使用持久記憶，所以無法參照先前的對話內容，要參照就得改用 AI agent。[A]
- 在 n8n 的範例中，對 chain 問「我上一個問題是什麼？」，就是用來對照 chain 沒有記憶的情況。[A]

### 示意：園遊會的固定流程
- 每天固定把報名表整理成名單、檢查欄位有沒有漏填（gate）、再寄通知信：步驟固定，適合 prompt chaining。
- 收到的問題先分成「場地」「繳費」「其他」三類，再交給各自的回覆範本：適合 routing。

## 四、適用情境與取捨

| 模式 | 什麼時候用 | 付出的代價 |
|---|---|---|
| Prompt chaining | 任務能輕鬆、乾淨地拆成固定子任務 [B]；可拆成較小、可驗證的步驟 [E] | 多步驟會增加延遲，換來準確度 [B] |
| Routing | 有明確類別、分開處理比較好，而且分類能做得準 [B] | 分類必須能做得準是前提 [B]；分錯類，後續就會進到不對的專門流程（本 Wiki 推論） |
| Parallelization | 子任務可同時跑以加速，或需要多種觀點、多次嘗試以提高信心 [B][E] | Voting 要把同一任務跑很多次 [B][E]，呼叫次數隨之增加（本 Wiki 推論） |
| Orchestrator-workers | 無法預測需要哪些子任務的複雜任務 [B]；子任務無法像平行化那樣事先定義 [E] | 子任務由 orchestrator 依輸入決定 [B]，換來彈性；事先無法完全知道會拆成哪些子任務（本 Wiki 推論） |
| Evaluator-optimizer | 有清楚的評估標準，反覆修改能帶來可衡量的價值 [B] | 迴圈會重跑生成與評估，直到通過為止 [E] |

- **判斷 evaluator-optimizer 合不合用的兩個訊號**：第一，人說出回饋後，LLM 的回應能明顯變好；第二，LLM 本身也能提供這樣的回饋。[B]
- **本 Wiki 對「推論」的標法**：表中標「本 Wiki 推論」的句子，是從來源定義直接推出的代價，不是來源原文；驗證時可對照前一欄的來源句。
- **整體取捨**：固定自動流用預先寫好的路徑換來可預測性與一致性 [B]；它適合「怎麼做已經想清楚」的任務，路徑寫不死的情況則見 02 單一 Agent。

## 五、常見錯誤

1. **把 n8n 的 chain 限制當成所有 workflow 的限制**：「沒有工具、沒有記憶」只是 n8n Basic LLM Chain 的產品定義 [A]；一般 workflow 的 LLM 可以帶工具、檢索與記憶 [B][E]。
2. **以為 orchestrator-workers 就是平行化**：兩者外形相似，但平行化的子任務是事先定義的，orchestrator-workers 的子任務是看輸入動態決定的。[B][E]
3. **分類不準還硬做 routing**：routing 適用的前提之一是分類能被準確處理。[B]
4. **沒有標準就做評估迴圈**：evaluator-optimizer 適合有清楚評估標準、反覆修改有可衡量價值的情況 [B]；沒有標準，就難以判斷何時算「可接受的回應」[E]。
5. **中間步驟不設檢查**：prompt chaining 可以在任何中間步驟加程式化檢查，確保流程還在正軌上 [B]；不設 gate，錯誤會一路傳到最後一步。
6. **把模式當規定**：這些是可以依用途組合與調整的常見模式，不是一定要照做的規範；只在能證明結果變好時才增加複雜度。[B]
